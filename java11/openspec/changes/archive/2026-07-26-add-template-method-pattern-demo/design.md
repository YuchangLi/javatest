## Context

项目是一个Java 11学习和演示项目，目前已实现7种设计模式：单例、适配器、装饰器、观察者、责任链、状态、策略。这些模式按功能组织在 `com.java11.design` 包下，每个模式都有独立的子包和演示类。

现有模式特点：
- 使用 Java 11 语言特性
- 集成 Lombok 减少样板代码
- 使用 SLF4J + Logback 日志
- 每个模式都有独立子包结构
- 演示类可独立运行（main方法）

项目使用 Maven 构建，编码为 UTF-8。

## Goals / Non-Goals

**Goals:**
- 添加模板方法模式的完整演示，展示其核心概念和应用
- 使用文件处理器作为演示场景，支持 CSV 和 JSON 格式
- 遵循项目现有的代码风格和包结构规范
- 清晰展示模板方法、抽象方法、钩子方法的区别和使用

**Non-Goals:**
- 不实现完整的文件处理库功能
- 不支持文件格式转换
- 不实现批量处理或并发处理
- 不集成现有的设计模式演示

## Decisions

### 1. 演示场景选择：文件处理器

**决策：** 使用文件处理器作为模板方法模式的演示场景

**理由：**
- 流程清晰（读取 → 转换 → 验证 → 写入），易于理解算法骨架
- 不同文件格式（CSV/JSON）需要不同的解析和序列化逻辑，适合展示抽象方法
- 数据转换步骤可选，适合展示钩子方法
- 与项目现有的设计模式应用场景（支付、订单状态）形成互补

**考虑的替代方案：**
- 数据处理管道（提取/转换/加载）：类似但更复杂，需要外部依赖
- 业务审批流程：项目已有状态模式处理订单审批，避免重复

### 2. 类结构设计

**决策：** 使用抽象类定义算法骨架，具体子类实现特定步骤

**理由：**
- 模板方法模式的核心是抽象类，不是接口
- 模板方法需要是 `final` 防止子类修改算法骨架
- 抽象方法强制子类实现，钩子方法提供可选扩展点
- 符合模板方法模式的经典实现方式

**类结构：**
```
AbstractFileProcessor (抽象类)
├── processFile() [final] - 模板方法
├── validateInput() [可重写] - 验证输入文件
├── readData() [abstract] - 读取数据（子类实现）
├── transformData() [钩子] - 数据转换（可选重写）
├── validateData() [可重写] - 验证数据
├── writeData() [abstract] - 写入数据（子类实现）
└── logResult() [可重写] - 记录结果

CSVProcessor extends AbstractFileProcessor
JSONProcessor extends AbstractFileProcessor
TemplateMethodDemo (演示类)
```

### 3. 数据传递方式

**决策：** 使用泛型 `<T>` 支持不同数据类型

**理由：**
- CSV 和 JSON 可能解析为不同的数据结构（List<String[]> vs Map）
- 泛型提供类型安全，避免强制类型转换
- 符合 Java 编码规范和最佳实践
- 保持接口简洁

**考虑的替代方案：**
- 使用 `Map<String, Object>`：灵活性高但失去类型安全
- 使用 `Object`：需要强制转换，不安全
- 定义统一的 `FileData` 接口：增加复杂度，对本演示不必要

### 4. 错误处理

**决策：** 抛出异常（IOException）并在演示类中处理

**理由：**
- 文件操作天然需要处理 IO 异常
- 保持代码简洁，专注于模式演示
- 在演示类的 main 方法中统一捕获和打印异常

**考虑的替代方案：**
- 返回结果对象（ProcessResult）：增加复杂度，对本演示不必要
- 使用日志记录：项目已有 SLF4J，可以补充使用

### 5. 钩子方法实现

**决策：** `transformData()` 提供默认空实现，子类可选重写

**理由：**
- 不是所有文件处理都需要数据转换
- 钩子方法的精髓就是提供可选扩展点
- 符合开闭原则：对扩展开放，对修改关闭

## Risks / Trade-offs

### 风险：抽象过度导致演示不够具体

**缓解措施：**
- 使用实际的文件格式（CSV/JSON）而非抽象概念
- 在演示类中创建测试数据文件，可直接运行
- 代码注释清晰说明每个方法的作用

### 权衡：简洁性 vs 完整性

**权衡：**
- 优先展示模板方法模式的核心概念，而非完整的文件处理功能
- 不实现复杂的文件格式验证、错误恢复等高级特性
- 保持代码量适中，专注于模式学习

### 权衡：Java 11 特性 vs 兼容性

**决策：**
- 使用 Java 11 特性（var、try-with-resources）
- 项目目标是 Java 11 演示，无需考虑向后兼容

## Migration Plan

本变更不涉及迁移：
- 新增代码，不修改现有代码
- 无数据库迁移或配置变更
- 无对外 API 变更

**部署步骤：**
1. 创建新包结构 `com.java11.design.template`
2. 创建抽象类和具体实现类
3. 创建演示类和测试数据文件
4. 运行演示验证功能

**回滚策略：**
- 直接删除新创建的文件即可
- 不影响现有代码
